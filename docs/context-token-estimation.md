# 上下文 Token 增量估算

`ContextManager` 在内存中维护 Token 估算值，降低短对话和工具续调的远程计数次数。

1. CLI 加载上下文后调用 `initialize_token_estimate(context.messages)`，只做本地估算。
2. 每次模型调用前，`compact_if_needed()` 根据已处理数量切出新增消息和工具事件，只估算新增内容。
3. 估算值小于压缩阈值时，直接继续，不调用 tokenizer。
4. 估算值达到阈值时，调用 tokenizer 精确计数，并将估算值校正为这个计数。
5. 精确计数未达到阈值时继续对话，后续新增量累加到校正后的基准上。
6. 精确计数达到阈值时，压缩旧消息、保留最近 `keep_recent` 条消息，然后对压缩后的上下文调用一次 tokenizer，以结果建立新基准。

CLI 当前的上下文上限是 128,000，阈值比例默认 0.8，因此达到 102,400 时触发检查。
如果剩下的消息全部属于需要保留的近期消息，当前逻辑不会强行压缩它们；精确计数超过上限会抛出 `ContextLimitExceeded`。
没有变化的上下文在完成检查后不会反复请求计数。

## 估算与缓存

`estimate_tokens(text)` 采用经验公式：ASCII 字符数 / 3 + 非 ASCII 字符数 × 1.5，向上取整。
每条消息另外预留 4 个 Token 的结构开销。该公式用于触发检查，不保证与模型分词一致。

只保存消息数量、工具历史数量、消息的本地估算小计，以及校正后的总量，不再保存快照或逐条估算数组。
正常对话按已处理数量读取新增切片，不遍历或比较旧消息，也不重新序列化旧工具事件。
一个布尔值标记当前内容是否已精确检查；追加内容时清除标记，完成检查后设置标记，避免重复计数。

工具调用参数、返回值以及 GLM 工具续调携带的 assistant 消息会计入工具历史。
新一轮 AgentLoop 清空临时工具历史时，用缓存的消息小计恢复本地估算基准；已经保存为普通消息的工具事件按照新增消息计入，避免重复累计。
这里不直接从真实总量中扣除工具估算量，避免估算高于真实值时得到负数。
正常消息和本轮工具历史只允许追加。压缩时主动调用 `initialize_token_estimate(messages, tool_history)` 重建缓存，随后用压缩后的真实计数校正总量。
如果以后增加编辑、删除、重排或切换会话功能，调用方须在修改后调用该初始化方法。当前只检查消息数量不能减少，不自动识别长度相同的内容改写。

估算缓存不写入会话文件，重启时重新估算。可通过 `estimated_tokens` 属性读取当前估算值。
未显式初始化的调用方也可以直接使用 `compact_if_needed()`，第一次调用会自动建立缓存。

计数范围沿用现有 ContextManager 的消息和序列化工具历史，不包含工具定义、服务端模板或预留输出，不能当作完整 API 请求的精确大小。
估算低估时仍可能遇到服务端上下文限制；当前改动没有增加服务端超限后的自动重试。

## 压缩失败处理

压缩结果通过 tokenizer 计数成功后，才会替换原始消息，防止计数失败导致原上下文提前丢失。
压缩后的精确计数仍超过上限时抛出异常；成功时同步更新调用方的消息列表和内存计数基准。
